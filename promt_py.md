### **ОСНОВНЫЕ ПРИНЦИПЫ (Нельзя нарушать)**
1.  **SOLID принципы:**
    *   **S** - Single Responsibility Principle: Класс/модуль должен иметь только одну причину для изменения.
    *   **O** - Open/Closed Principle: Программные сущности должны быть открыты для расширения, но закрыты для модификации.
    *   **L** - Liskov Substitution Principle: Подклассы должны замещать базовые классы, не нарушая работу программы.
    *   **I** - Interface Segregation Principle: Лучше создавать много специализированных интерфейсов (протоколов/абстрактных классов), чем один универсальный.
    *   **D** - Dependency Inversion Principle: Модули верхнего уровня не должны зависеть от модулей нижнего уровня. Оба должны зависеть от абстракций.
2.  **Модульность:** Каждый модуль находится в отдельной папке с собственным пространством имен. Код должен быть организован так, чтобы его можно было легко тестировать изолированно.
3.  **Инкапсуляция:** Все, что может быть приватным (начинаться с `_`), должно быть приватным. Запрещено использовать защищенные/приватные члены классов извне.
4.  **Читаемость:** Код должен быть самодокументируемым. Комментарии объясняют **ПОЧЕМУ**, а не **ЧТО**. Имена переменных, функций и классов должны быть говорящими. Закомментированный код запрещен.
5.  **Типизация:** Обязательно использование аннотаций типов (type hints) для всех функций и методов.

*   Функции и методы — **`snake_case`**.
*   Переменные — **`snake_case`**.
*   Константы — **`UPPER_CASE`**.

### **3. РАЗРАБОТКА МОДУЛЕЙ (Критически важно)**

#### **3.1 Структура модуля**
Каждый модуль должен быть изолирован и предоставлять четкий публичный интерфейс.

```
module_name/
├── __init__.py                 # Публичный API модуля (экспортирует только нужное)
├── interfaces.py                # Интерфейсы/протоколы модуля
├── domain.py                    # Модели данных модуля
├── service.py                   # Реализация бизнес-логики
├── exceptions.py                # Исключения модуля
└── repositories.py              # Работа с данными (если есть своя БД)
```

#### **3.2 Правила для `__init__.py`**
```python
"""Модуль для работы с [функциональность]."""

from .service import MainService
from .domain import Entity
from .exceptions import ModuleError

__all__ = [
    "MainService",
    "Entity",
    "ModuleError",
]
```

#### **3.3 Dependency Injection**
*   Использовать внедрение зависимостей через конструкторы классов.
*   Зависеть от абстракций (протоколов/ABC), а не от конкретных реализаций.
*   Для сложных графов зависимостей использовать контейнеры (например, `dependency-injector`).

Пример:
```python
from abc import ABC, abstractmethod

class Repository(ABC):
    @abstractmethod
    def get(self, id: int) -> Entity:
        pass

class Service:
    def __init__(self, repo: Repository) -> None:
        self._repo = repo  # Зависим от абстракции, не от конкретной БД
```

### **5. КОНФИГУРАЦИЯ**

*   Использовать переменные окружения для конфигурации (библиотека `pydantic-settings`).
*   Файл `.env` для локальной разработки (не коммитить!).
*   Все настройки валидируются через Pydantic модели.

Пример `config.py`:
```python
from pydantic_settings import BaseSettings

class Settings(BaseSettings):

    debug: bool = False
    database_url: str
    
    class Config:
        env_file = ".env"

settings = Settings()
```
