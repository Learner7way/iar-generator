### **2. СТИЛЬ КОДИРОВАНИЯ (C99)**

#### **2.1 Форматирование**
*   **Отступы:** 4 пробела. Никаких табуляций.
*   **Кодировка:** UTF-8.
*   **Фигурные скобки:** **Только** стиль K&R (открывающая скобка на той же строке). Стиль должен быть единообразен во всем проекте.
    ```c
    if (condition) {
        // code
    } else {
        // code
    }
    ```
*   **if-else:** Скобки `{}` обязательны, кроме случаев с очень простым действием в одной строке (`if (cond) return 0;`). Если одна ветка использует `{}`, другая обязана их использовать тоже.
*   **Составные условия:** Каждое подусловие на новой строке, логические операторы (`&&`, `||`) — в начале строки.
    ```c
    if ( (some_long_condition_1 != 0)
         && (some_long_condition_2 > SOME_THRESHOLD)
         && (some_long_condition_3 == true) ) {
        // code
    }
    ```
*   **switch:** Всегда должен содержать метку `default:`.
*   **Пробелы:**
    *   Ставятся после ключевых слов: `if`, `switch`, `case`, `for`, `do`, `while`.
    *   Ставятся вокруг бинарных и троичных операторов (`=`, `+`, `==`, `? :` и т.д.).
    *   Не ставятся после `sizeof`, `__attribute__`, вокруг унарных операторов (`*`, `&`, `++`), и у операторов доступа `.` и `->`.

#### **2.2 Комментарии**
*   **Блок кода:** На отдельной строке, отступ совпадает с кодом.
*   **Локальные:** На той же строке, начиная с позиции ~120 символов.
*   **Смысл:** Содержат информацию "почему?", а не "что?"
    ```c
    uint32_t counter = 0; // таймеру нужен 32битный беззанаковый счётчик 
    ```
*   **Описание функций (Doxygen style):** Обязательный блок перед прототипом в `.h` файле.
    ```c
    /**
     * @brief       Краткое описание действия функции.
     * @param[in]   param1 - описание входного параметра.
     * @param[out]  param2 - описание выходного параметра.
     * @return      Значение, описывающее результат работы.
     */
    void module_function(uint8_t param1, uint32_t *param2);
    ```
*   **ЗАПРЕЩЕНО:** Оставлять закомментированный код. Использовать `#if 0 ... #endif` для временного исключения блоков.

*   **Переменные и функции:** **ТОЛЬКО `snake_case`**. Имя всегда начинается с префикса модуля.
    *   *Пример:* `modem_send_answer()`, `storage_current_record`, `gui_update_display()`.
*   **Глобальные переменные:** (Использовать с большой осторожностью). Формат: `модуль_имя_переменной`. Пример: `modem_status_flags`.
*   **Статические переменные:** Формат: `s_имя_переменной` или просто `имя_переменной`.
*   **Макросы и дефайны:** **ТОЛЬКО `UPPER_CASE`** с подчеркиваниями. Макросы-действия всегда с круглыми скобками: `#define LED_ON()`

### **4. ТИПЫ ДАННЫХ И ОБЪЯВЛЕНИЯ**

*   Использовать только типы из `stdint.h`: `uint8_t`, `int32_t`, `uint64_t` и т.д.
*   `typedef` **никогда** не скрывает указатель (кроме указателей на функцию).
*   Не более двух уровней косвенности (`uint32_t **ptr` допустимо, `uint32_t ***ptr` — нет).
*   Запрещено объявлять несколько переменных в одной строке.

### **5. ВЕРСИОНИРОВАНИЕ И КОНФИГУРАЦИЯ СБОРКИ**
Версия должна состоять из четырех основных частей и одной опциональной: `PRODUCT_ID.PRODUCT_VERSION.PRODUCT_VARIANT.PRODUCT_HARD[.VERSION_REVISION]`

*   **`defs.h`** — задает `PRODUCT_ID`, `PRODUCT_VERSION`, `VERSION_REVISION` и варианты сборки `BUILD_*`.
*   **`plat.h`** — задает целевую платформу (версию схемы и вариант исполнения).
*   **`version.h`** — на основе `defs.h` и `plat.h` определяет конечный `PRODUCT_HARD`, включает нужный `hard_*.h` и управляет функциональными ключами `VARIANT_*`.
*   **Золотое правило конфигурации:** Для получения новой сборки должны изменяться **только** файлы `defs.h` и `plat.h`. Никакие другие файлы проекта для смены конфигурации не правятся.

### **6. РАЗРАБОТКА МОДУЛЕЙ (Критически важно)**

#### **6.1 Общие требования к модулю**
*   Для подключения модуля достаточно одного заголовочного файла `<module>.h`.
*   `<module>.h` **не должен** включать в себя другие заголовочные файлы (исключение — `<module>_config.h`).
*   Если модуль состоит из нескольких файлов, файлы нижнего уровня именуются как `<module>_<description>.[ch]` (например, `gui_draw.c`, `gui_input.c`).
*   Рекомендации по размеру: простой модуль (`.c` файл) до 300 строк, функция — до 24 строк.
*   Модуль должен иметь версию в формате SemVer (может храниться в `<module>.h`).

#### **6.2 Структура файла `<module>.c` (Строгий порядок секций)**
1.  **Includes (строгий порядок):**
    *   Заголовочные файлы стандартной библиотеки С (`<stdint.h>`, `<stdbool.h>`, `<string.h>` и т.д.)
    *   Заголовочные файлы архитектуры/ОС (`FreeRTOS.h`, `cmsis_os.h`)
    *   **Свой заголовочный файл `<module>.h`.** (Самый важный пункт!)
    *   Заголовочные файлы других модулей, от которых зависит данный.
    *   Заголовочные файлы платформозависимой реализации (`*_prphr.h`).
2.  **Private Defines & Macros**
3.  **Private Typedefs / Enums**
4.  **Private Variables** (все `static`)
5.  **Private Function Prototypes** (все `static`)
6.  **Private Function Implementations** (все `static`)
7.  **Public Function Implementations** (из `<module>.h`)

#### **6.3 Структура файла `<module>.h`**
*   Содержит только публичный интерфейс API.
*   **Не содержит объявлений переменных.**
*   Может содержать как **прямой интерфейс** (функции, вызываемые извне), так и **инверсный интерфейс** (функции обратного вызова, которые должны быть реализованы вызывающим кодом). Инверсный интерфейс может быть реализован через `extern` (обязательно), `__weak` (опционально) или через таблицы указателей на функции.
